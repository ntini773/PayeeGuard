# New destination-change flow: sandbox verification

Prepared 2026-11-11. **Do not execute PayPal calls until the user explicitly says
“go”.** Claude Code drives the browser after that approval. The user handles any
CAPTCHA/2FA personally. No live credentials, live endpoints or real-money calls.
Each payout is **USD 0.01**. Two distinct legitimate test earnings are needed to
show A before activation and B after: total USD 0.02 sandbox payout principal
(allow additional sender balance for any applicable sandbox fee).

PayPal describes sandbox account credentials and password management in its
[Sandbox accounts guide](https://developer.paypal.com/sandbox-testing/accounts).
Its [Identity scope reference](https://developer.paypal.com/log-in/references/)
maps both payer ID and account verification status to
`https://uri.paypal.com/services/paypalattributes`. The authorization request needs
`openid https://uri.paypal.com/services/paypalattributes`. This backend does not
require profile/email/address scopes to authorize the destination.

### Redirect URI and transport

NEW and OLD both use one registered URI:
`http://127.0.0.1:8765/api/v1/paypal/callback`. Their purpose is in the server's
nonce binding, not a different URL. The old `/callback` belongs to the legacy flow
and does not replace this registration; retain both registrations only if testing
both flows. No trailing slash is generated by this backend. Scheme, host, port,
path and trailing slash must match the registered URI; port 8765 is significant.
Do not substitute localhost, a different port, `/callback`, or a slash suffix.
PayPal's [button reference](https://developer.paypal.com/log-in/build-button/)
requires the encoded return URL to match the Dashboard Return URL.

For local development use numeric loopback 127.0.0.1 with HTTP. The primary
[Keycloak PayPal integration guide](https://www.keycloak.org/docs/latest/server_admin/#_paypal)
explicitly instructs replacing localhost with 127.0.0.1 for PayPal return URLs.
The current PayPal pages retrieved for this preparation did not explicitly define
the scope of the HTTP-loopback exception; **Dashboard acceptance of the exact
local URI and the real redirect remain verification gates**, not a claimed tested
result. If this app's settings reject HTTP loopback, stop and use a registered
HTTPS origin/tunnel instead; do not bypass URI checking. For a non-loopback host,
use HTTPS, export RESCUE_PUBLIC_ORIGIN to the exact HTTPS origin, register
`ORIGIN/api/v1/paypal/callback`, and access the entire site at that origin.
The backend emits Secure cookies/HSTS for that mode; TLS terminates at the proxy.
Never mix localhost/127.0.0.1 or HTTP/HTTPS between login and callback: the original
marketplace session cookie must return with the callback.

## Numbered runbook and expected results

1. **Prepare locally without provider calls.** Run `pixi install --locked` and
   `pixi run test`. Use the existing built `ui/dist`; the Python backend serves it
   at the same origin, with SPA fallback. Do not use the simulated seed for a real
   sandbox run. Confirm NVIDIA configuration privately if the UI invokes it.
   Configure RESCUE_COOLING_SECONDS *before creating any case* and keep it constant.
   Default is three days. For the requested rapid sandbox smoke check, the user
   may explicitly set `RESCUE_COOLING_SECONDS=1` in .env; this is honored as policy
   configuration, not a timer override. Policy/evidence/review checks still apply.
   A one-second cooldown is too short to manually demonstrate a pre-activation
   payout after approval: perform the A payout while pending, before approval.

2. **Create a clean sandbox-only DB and established A record.** The following
   local-only script creates a new temporary runtime, independent local login
   passwords and the payee entitlement; it does not call PayPal. Enter A's exact
   payer ID privately. Save the printed runtime path as RUNTIME below.

   ```bash
   pixi run python - <<'PY'
   import getpass, json, os, secrets, tempfile
   from pathlib import Path
   from rescue.store import Store
   from rescue.destination_store import DestinationStore
   os.umask(0o077)
   root = Path(tempfile.mkdtemp(prefix='payee-sandbox-'))
   store = Store(root / 'app-sandbox.sqlite3')
   with store.connect() as db:
       db.execute('INSERT INTO metadata VALUES (?,?)', ('mode', 'sandbox'))
   credentials = {}
   for user, role in [('creator', 'recipient'), ('operator', 'operator')]:
       credentials[user] = secrets.token_urlsafe(24)
       store.add_user(user, role, credentials[user])
   dest = DestinationStore(store)
   dest.provision_grant('creator', 'sandbox-verification', 'seller-1', manage=True)
   dest.provision_grant('operator', 'sandbox-verification', 'seller-1', review=True)
   payer = getpass.getpass('Exact established sandbox payer ID A (hidden): ')
   dest.provision_payee('sandbox-verification', 'seller-1', payer, cap='0.01', currency='USD')
   token = store.login('creator', credentials['creator'])
   with dest.connect() as db:
       assert dest.payee(db, dest.principal(token))['active_payer_id'] == payer
   store.logout(token)
   credential_path = root / 'sandbox-accounts.json'
   credential_path.write_text(json.dumps(credentials))
   credential_path.chmod(0o600)
   print('Runtime:', root)
   print('Local marketplace credentials saved privately:', credential_path)
   print('Stored active_payer_id exactly equals provided A: YES')
   PY
   ```

   Expected: new empty change queue, A is the active trusted destination, no B,
   no earning/payout. This creates no fabricated legacy PayPal payout item.
   User confirms that the entered A ID belongs to their sandbox account A.

3. **Provision two trusted earnings (still no PayPal call).** Replace RUNTIME
   literally with the printed directory; both commands are idempotent by earning
   ID and reject unknown payees. Output masks the earning identifier.

   ```bash
   pixi run python -m rescue.destination_admin --database RUNTIME/app-sandbox.sqlite3 --mode sandbox earning --tenant sandbox-verification --seller seller-1 --earning-id before-activation --amount 0.01 --currency USD
   pixi run python -m rescue.destination_admin --database RUNTIME/app-sandbox.sqlite3 --mode sandbox earning --tenant sandbox-verification --seller seller-1 --earning-id after-activation --amount 0.01 --currency USD
   pixi run python -m rescue.app serve --mode sandbox --ai nvidia --runtime-dir RUNTIME
   ```

   Expected: ONE site at `http://127.0.0.1:8765`, healthz OK, built UI on root/deep
   links, /api/session still JSON. Local marketplace passwords are in the private
   sandbox-accounts.json, not PayPal passwords. If no dist exists, static/ remains
   the fallback. No payment or OAuth request is made merely by provisioning.

4. **Stop for the user's GO.** Confirm sandbox-only app, registered return URL,
   feature/scopes, A/B credentials available privately, A equality and funded
   sender. Claude Code begins the interactive/provider steps only after GO.

5. **Seller requests B.** Sign in as creator. POST
   `/api/v1/destination-change-requests` with reason_text and Idempotency-Key;
   subsequent mutations require X-CSRF-Token from `/api/session`.
   Expected CHANGE_REQUESTED, A active, proposed_destination_usable=false.
   Record case ID/version, not cookies or tokens.

6. **Authenticate NEW B.** POST `{}` to
   `/api/v1/destination-change-requests/CASE/auth/NEW`. Open authorization_url in
   the same browser session. It must be on `https://www.sandbox.paypal.com/connect`.
   Log into sandbox B, allowing account-information consent. Sign out of any
   remembered A login on PayPal first if necessary, without clearing the local
   marketplace session. User completes any CAPTCHA/2FA. The backend exchanges
   the code server-side at its fixed sandbox API base. Expected callback at the
   new URI, new status VALIDATED, state PENDING_OLD_ACCOUNT_AUTH, A still active,
   B only proposed. If PayPal auto-selects A, same-ID outcome ACTIVE/ALLOW_NO_CHANGE
   is correct; create a new case and deliberately use distinct B.

7. **Prove the A payout before activation.** As operator, POST `{}` to
   `/api/v1/marketplace-payouts/before-activation/execute`, with CSRF. This invokes
   the real sandbox provider for USD 0.01. Expected receiver is backend-stored A,
   never proposed B. A replay uses the same saved operation; never choose a new
   earning ID to evade an UNKNOWN result. Record masked receiver evidence from
   sandbox activity and sender_batch_id, excluding response tokens/credentials.

8. **Authenticate OLD A.** Sign back into the same creator marketplace identity
   (new marketplace sessions require a freshly started auth attempt). POST `{}`
   to `/api/v1/destination-change-requests/CASE/auth/OLD`; authenticate PayPal A
   at the sandbox site. Expected exact A match, state PENDING_REVIEW, A active,
   B still blocked, no approval. Callback replay must fail and must not exchange
   the code again. Avoid capturing callback URLs containing codes/state in reports.
   A wrong account produces NOT_MATCHED plus reviewer-only OLD_ACCOUNT_MISMATCH;
   stop normal approval and follow controlled recovery review. Do not fake a match.

9. **Trusted marketplace evidence.** As local backend operator record the actual
   reviewed entitlement (fixture marketplace evidence, not a claim of production
   KYC). Use current version after the callback:

   ```bash
   pixi run python -m rescue.destination_admin --database RUNTIME/app-sandbox.sqlite3 --mode sandbox evidence --user operator --case CASE --kind SELLER_ENTITLEMENT --reference sandbox-reviewed-record --reason 'Reviewed sandbox marketplace entitlement' --accepted --version VERSION
   ```

   The console prompts for the local operator password privately. Expected evidence
   record with verifier/time/reason and an incremented version. Lost/mismatched A
   requires ACCOUNT_RECOVERY and the longer configured recovery cooldown instead.

10. **Review and cooling-off.** As operator POST `/review` with APPROVE, reason and
    current expected_version. Expected APPROVED_COOLING_OFF only, no immediate B
    activation. A stale version returns 409; reload rather than changing booleans.
    Read/gate processing after the configured deadline rechecks evidence, current
    approval role, policy and version, then atomically updates active destination
    and case to ACTIVE_NEW_DESTINATION. Queue GET also progresses these timers.
    With a one-second test setting this can happen on the next read; no simulation
    endpoint or direct DB deadline edit is allowed. Keep config stable throughout.

11. **Prove B after activation.** POST `{}` as operator to
    `/api/v1/marketplace-payouts/after-activation/execute`. Expected USD 0.01 to B,
    selected only from the updated stored payee. Verify the receiver privately in
    sandbox activity. No JSON payer-ID/amount override is accepted.

12. **Reconcile both earnings.** POST `{}` to each earning's `/reconcile` endpoint.
    Expected matched sender batch, receiver, item, amount and currency. SUCCESS
    yields RECONCILED and needs_attention=false. PENDING is nonterminal, continue
    read reconciliation. UNCLAIMED/ONHOLD or FAILED/RETURNED/BLOCKED/DENIED require
    operator attention; no automatic replacement. UNKNOWN/RECONCILE_REQUIRED must
    not be labelled paid. A later read failure keeps a prior confirmed result and
    emits PAYOUT_RECONCILE_FAILED; retain that operational failure in the report.
    If a create timed out without a provider batch ID, use trusted provider records
    and backend manual reconciliation; do not submit a new earning to compensate.

13. **Evidence/report.** Record masked A/B, case/state/version transitions, policy
    version/deadline, provider statuses, payout amount/currency, operation identity,
    needs_attention, and failed tests/debug identifiers. Distinguish real PayPal
    identity/payout from fixture marketplace evidence and live AI advisory output.
    Preserve this runtime for restart/reconciliation; restore normal cooldown only
    for a fresh test run, because configuration changes invalidate prior approvals.

## Failure modes

| Symptom | Meaning / response |
|---|---|
| redirect_uri mismatch / invalid client or return URL | Wrong app/environment or exact registered URI mismatch. Compare scheme, 127.0.0.1, port, path and slash; the token exchange uses the same URI. Do not fall back to legacy /callback. |
| invalid_scope or missing payer_id/verified_account | Scope not enabled/consented on this app. Confirm Log in with PayPal and account-information attributes; request openid plus paypalattributes. Do not weaken required identity attributes. |
| verified_account false / identity callback rejected | Backend cannot accept an unverified sandbox account as trusted evidence. Confirm account/bank/email verification state in sandbox settings; use a verified test account. Do not change the gate to accept false. |
| old payer ID mismatch | Logged in to B/another remembered account instead of A, or wrong stored entitlement. New B login never satisfies OLD. Case goes to recovery review, not approval. |
| 403 / PAYOUT_NOT_AVAILABLE / permission denied | App-linked sender is not eligible or lacks Payouts permission; OAuth success alone is not Payouts access. Check sandbox Business sender/country and app capability. Preserve intent; reconcile before retry decisions. |
| INSUFFICIENT_FUNDS / insufficient balance | Sender's sandbox balance is too low for payout plus applicable fee. Fund that Business sender; do not assume recipient A/B balance funds the sender. Reconcile persisted attempt; never blindly create a replacement. |
| invalid/replayed state or lost session | Wrong/expired session, case, purpose/version or already consumed nonce. Start a fresh auth attempt in the intended marketplace session. No code/state is accepted as an assertion of identity. |
| APPROVAL_STALE after configuration change | Policy/version or reviewer authorization changed. Re-review using current evidence and version; never rewrite approval metadata or shorten a stored deadline manually. |
